# 코드 리뷰를 이번 코드로 이해하기

코드 리뷰는 변경안을 읽고 의도·실제 동작·위험·검증 근거를 확인하는 과정입니다. QA에서 재현 조건과 기대 결과를 맞추는 경험을 코드의 입력·분기까지 확장한다고 생각하면 연결하기 쉽습니다.

## 이번에 따라간 다섯 질문

1. 어디서 실행되나요? Dockerfile → assemble_runtime.py → system-runtime/main.py를 확인했습니다.
2. 무엇을 입력하나요? 사용자가 지정하는 출력 경로입니다.
3. 어떤 입력이 위험한가요? 이미 중요한 파일이 들어 있는 경로입니다.
4. 왜 문제가 생기나요? 복사 전에 기존 폴더 전체를 삭제하기 때문입니다.
5. 바뀐 코드를 어떻게 믿나요? 보존 테스트가 수정 전 실패하고 수정 후 통과하는지, 새 경로 조립도 유지되는지 확인했습니다.

## 변경 전과 후

변경 전 핵심:

```python
output = output.resolve()
if output.exists():
    shutil.rmtree(output)
```

변경 후 핵심(전체 코드는 tools/assemble_runtime.py):

```python
if output.is_symlink():
    raise FileExistsError(...)
output = output.resolve()
if output.exists():
    raise FileExistsError(...)
output.mkdir(parents=True, exist_ok=False)
```

새 출력 경로만 받는 계약을 명확히 정했습니다. 그래서 README와 호출자에게 보이는 오류도 함께 검토해야 합니다.

## 실제 리뷰 코멘트 예시

> 기존 폴더를 --output으로 지정하면 50행의 rmtree가 폴더 안 파일도 지웁니다. 임시 notes.txt로 재현했습니다. 기존 경로는 중단하도록 바꾸고 파일 보존과 새 출력의 정상 조립을 함께 테스트하면 좋겠습니다.

좋은 코멘트는 위치 → 재현 조건 → 영향 → 수정 방향 → 검증 방법을 연결합니다. 취향이나 막연한 “위험해 보여요”만으로 결함을 확정하지 않습니다.

## 이번에 익힐 구분

| 개념 | 이 코드에서의 의미 |
|---|---|
| 리팩터링 | 외부 동작을 유지하며 구조를 개선. 이번 기존 경로 거부는 동작이 달라지므로 안전 버그 수정 |
| 회귀 테스트 | 새 경로의 복사 결과와 기존 백엔드 기능이 수정 뒤에도 유지되는지 확인 |
| 특성 확인 테스트 | metadata-v3가 현재 무엇을 하는지 기록. 설계가 올바르다는 과학적 증명은 아님 |
| 하드코딩 검토 | 0.50이라는 모양보다 근거·의미·변경 주체·영향을 확인 |
| 단일 원본 | 실제 조립에 쓰이는 main.py와 검토용 복본을 구분 |
| 테스트의 한계 | HTTP/모의 클라이언트 통과가 실제 AI·브라우저·보안 검증을 대체하지 않음 |

`0.50 × 0.15 = 0.075`는 0~100 표시에서 7.5%p 기여입니다. “실제로 절반의 출처와 일치했다”는 뜻이 아닙니다. 가중치를 바꾸거나 값만 없애면 정책 변경이므로 별도 영향 분석이 필요합니다.

직접 리뷰할 때는 “기존 출력이 있을 때 왜 중단하나요?”, “이 테스트가 원래 코드에서도 통과했나요?”, “79건으로 무엇까지 확인했고 무엇은 남았나요?”를 설명해 보시면 됩니다. 답은 위 코드·TC·기준선에서 찾을 수 있습니다.
